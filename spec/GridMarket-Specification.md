### 1.1 Background

**BLUF:** Home batteries can shift load in the hours ERCOT prices spike, and GridMarket turns that flexibility into a tradable, explainable, simulated product.

**Frame**

- **Who:** Battery owners represented by bots, provider companies, and traders.
- **What:** The market need: a price signal for one kWh of battery flexibility in one delivery hour.
- **Why:** Real-time and day-ahead ERCOT prices diverge when load, outages, and congestion rise, and flexibility is worth most then.
- **How:** A Flex Credit market with spot and future products per load zone, priced against ERCOT settlement point prices.
- **When:** Every delivery hour, starting on the hour in America/Chicago time.
- **Where:** The four ERCOT load zones LZ_HOUSTON, LZ_NORTH, LZ_SOUTH, and LZ_WEST.

ERCOT publishes real-time and day-ahead settlement point prices, load
forecasts, outage capacity, and binding transmission constraints through its
Public API. Those signals predict when grid stress raises the value of
flexible load. GridMarket defines a Flex Credit as 1 kWh of battery
flexibility for one delivery hour and prices it in $/credit, where
$/MWh ÷ 1000 = $/credit (DEC-GM-008).

The hackathon entry targets the Open Grid Data and Most Commercializable
tracks (DEC-GM-003). The market is simulated: no real settlement, billing,
money, KYC or AML, QSE registration, blockchain, options, leverage, or
sophisticated margin is in scope. A Flex Credit is not a renewable energy
certificate, a cryptocurrency, or a claim on specific electrons, and future
products are simulated forward flexibility contracts, not regulated
commodity futures.

#### System context

**BLUF:** GridMarket's boundary encloses the market app and its bot container, and every external party reaches it only through the tunnel, the host loopback, or the owner's ERCOT Worker.

**Frame**

- **Who:** Judges and traders, the owner, the bot population, the ERCOT Worker, ERCOT, NWS, and the optional hosted Jev service.
- **What:** The system boundary and every flow that crosses it.
- **Why:** To show that live ERCOT data enters only through the Worker and that the market is exposed only through an outbound tunnel.
- **How:** Docker Compose services bound to 127.0.0.1, an outbound Cloudflare named tunnel, and an HTTP client of the Worker.
- **When:** Whenever the stack runs; the tunnel is live from the Sunday recording through 15:00 CDT.
- **Where:** The spectre-dev workstation and the owner's Cloudflare account.

The market app is one FastAPI process that serves the REST API and the built
dashboard. The bot population runs in a second container and calls the same
public API over HTTP with its own keys. Judges and traders reach the app only
through an outbound Cloudflare named tunnel; the app binds its HTTP port to
127.0.0.1 on the host and runs as a non-root user (AC-GM-OPS-01). Admin
requests arrive only on the host loopback without a `CF-Connecting-IP`
header.

The market reads ERCOT signals only through the owner's ERCOT Worker, which
holds the ERCOT credentials, its 55-minute token cache, and the ERCOT
request budget. The market holds no ERCOT credential; it reads the Worker
URL and the market client key only from the untracked `.env` file, and never
writes them to the repository, to logs, or to API responses (AC-GM-DATA-04).
The Worker's 3D views read market activity and router results back from the
market by cross-origin GET. NWS weather data comes keyless from
`api.weather.gov`. The hosted Jev service is called only when the owner sets
`GRIDMARKET_JEV=on`.

### 1.4 Scope and Non-Goals

**BLUF:** GridMarket simulates a flexibility market end to end and deliberately excludes every real-money, regulatory, and speculative-infrastructure concern.

**Frame**

- **Who:** The owner, judges, and every implementer deciding whether a change is in scope.
- **What:** What the MVP does and does not attempt.
- **Why:** A hackathon schedule leaves no room for real settlement or compliance, and pretending otherwise would mislead judges.
- **How:** List exclusions explicitly and cut rather than stub any excluded capability.
- **When:** Fixed for the Lifecycle; changes need an owner decision.
- **Where:** The technical plan's Exclusions section.

In scope: live ERCOT and NWS signals, an explainable opportunity score, spot
and future Flex Credit products per zone, one matching engine with risk
controls and an append-only ledger, simulated providers and batteries, a
seeded bot population with an economy, a decision router, a multi-page
dashboard, the Python SDK, sandbox onboarding, and agent-readable
documentation.

Out of scope: real settlement, billing, money, KYC and AML, QSE
registration, blockchain, options, leverage, and sophisticated margin;
Google OAuth, a personal bot, a first-party AI trading agent, WebSockets, a
historical backtesting dashboard, and sophisticated clearing; a remote MCP
server; bot evolution and bot retirement; judges spawning bots; a log stack;
a TypeScript SDK or example; wind and solar forecast signals; record-and-replay
data in the live data path; special-events and TxDOT traffic feeds; and
porting code from private repositories.

### 1.5 Assumptions and Constraints

**BLUF:** GridMarket assumes the owner deploys the ERCOT Worker and the tunnel, and constrains itself to one host, one process, one SQLite file, and dependencies at least 14 days old.

**Frame**

- **Who:** The owner and the Integration Engineer.
- **What:** The conditions the architecture relies on and the limits it accepts.
- **Why:** Making assumptions explicit turns a missed one into a named gap instead of a surprise.
- **How:** Each assumption has a fallback; each constraint is marked in code with a `ponytail:` comment where it caps behavior.
- **When:** Through the demo recording on Sunday 2026-09-27.
- **Where:** The spectre-dev workstation, the owner's Cloudflare account, and ERCOT's Public API.

Assumptions. The owner registers the ERCOT account, sets the Worker secrets,
and deploys the Worker with the report allowlist and market client key before
the phase 1 acceptance run (DEC-GM-027); until then tests run on fixtures
shaped like Worker responses (RISK-GM-02). The owner creates the tunnel
credentials and starts the `tunnel` profile. ERCOT and NWS stay reachable
most of the time; when they do not, the market serves stale values with their
age.

Constraints. One workstation hosts the stack (RISK-GM-03). SQLite in WAL mode
serializes every write transaction, which caps throughput at one writer. The
rate limiter lives in process memory, so a restart resets buckets. Every new
dependency must have a release public for at least 14 days (DEC-GM-020). No
lane edits a frozen file without a recorded contract amendment.

#### 4.1.1 Market and risk engine

**BLUF:** Every order passes authentication, rate limit, idempotency, halt, and risk checks and is matched and booked in one `BEGIN IMMEDIATE` transaction, so no order sequence can break the ledger or over-reserve a battery.

**Frame**

- **Who:** Any client submitting an order: judges, bots, strategies, and agents.
- **What:** Product listing, order submission, the risk controls, and price-time matching (DES-GM-MARKET, DES-GM-RISK).
- **Why:** Market integrity: capacity and cash checks must not race.
- **How:** Serialized SQLite write transactions and a pure `MatchingEngine.match` function.
- **When:** Products listed every hour; orders on each `POST /v1/orders`.
- **Where:** `market.py` and `api.py`.

Every hour the settlement tick lists, per zone, spot products for delivery
hours 1–2 hours ahead and future products for 3–24 hours ahead, and closes
products whose delivery hour has started; both types trade through one
matching engine (AC-GM-MKT-01). The API also accepts the alias
`FLEX-<zone>-<HH>` for the next future product with delivery hour `HH`.

Order submission runs in one transaction: authenticate the key (401),
rate-limit per key (429), check the Idempotency-Key (400 missing, 409
different body, replay on identical body), check halts (423
`MARKET_HALTED`) and provider status (422 `PROVIDER_OFFLINE`), apply the risk
controls (422 with a typed reason), match, apply fills to the ledger, append
`trades` and `events`, store the idempotent response, and commit.

The risk controls are never cut. An order larger than 50 credits, an order
that would raise the absolute net position in a product above 200 credits,
or an order that needs more cash than cash minus holds of open orders is
rejected with a typed reason and changes no balance (AC-GM-MKT-04). Cash held
by an order is limit price × quantity for every buy and every future sell. A
spot sell instead reserves capacity per battery through
`ProviderAdapter.reserve_capacity` in the same transaction, never more than
state of charge minus minimum reserve minus existing reservations, so
concurrent sells cannot over-reserve (AC-GM-MKT-03).

The engine fills an incoming limit order in price-time priority at each
resting order's price, and each fill is recorded exactly once in the
append-only trade ledger, whose SQLite triggers abort any UPDATE or DELETE
(AC-GM-MKT-02). A spot fill moves price × quantity of simulated cash from
buyer to seller and adds the quantity to the buyer's Flex Credit inventory
(AC-GM-MKT-06). The figure shows the order states.

#### 4.1.2 Settlement, ledger, and bot economy

**BLUF:** Settlement is driven by stored ERCOT real-time prices and the ledger alone, so every balance, loss statistic, and bot state can be rebuilt after a restart.

**Frame**

- **Who:** Every account holder; bots through the payroll tick.
- **What:** Spot delivery, future expiry, settled positions, deposits, and startup seeding (DES-GM-SETTLE, DES-GM-ECON).
- **Why:** Market integrity and explainable P&L; deposits must never look like trading profit.
- **How:** Hourly settlement tick and 60-second payroll tick, each one transaction.
- **When:** At each delivery hour's end and each bot's pay time.
- **Where:** `market.py`, `economy.py`, and the `settled_positions` and `deposits` tables.

When a spot delivery hour ends, the tick calls `verify_delivery`; the
reservation is released and the commitment recorded as delivered, or as a
default with the buyer refunded when the provider reports the asset offline.
When all four 15-minute NP6-905-CD real-time prices of a future product's
delivery hour are stored, the reference price is their mean ÷ 1000 $/credit,
and each open position receives cash (reference − average price) × signed
quantity (AC-GM-MKT-05). There is no margin model, so an extreme price can
drive a short position's cash below zero; the dashboard shows it. Unrealized
P&L marks open futures at the last trade, else the mid, else the prediction's
expected value.

When the database is empty at startup, the system seeds the bot population
with starting cash, zero Flex Credits, one API key, and the sampled
batteries; human and judge sandbox accounts start with $1,000.00
(AC-GM-ACCT-01). Every 30 minutes, at a fixed per-bot offset, each employed
bot's pay is appended as a deposit, which is not a trade and changes no P&L
(AC-GM-ECON-02). A settled position with negative realized P&L counts as one
loss; a dormant bot gets no bailout (AC-GM-ECON-03). After a restart, every
bot's parameters, cash, positions, and dormant status equal the values rebuilt
from the ledger and the master seed (AC-GM-ECON-04).

#### 4.1.4 Explainable opportunity score

**BLUF:** The opportunity score is a weighted sum of seven squashed factors, monotonic by construction, and every point of it is attributed to a named factor with a one-line explanation.

**Frame**

- **Who:** Judges, traders, and bots that read predictions.
- **What:** The score, level, confidence, expected value, and drivers for each zone and future delivery hour (DES-GM-SCORE).
- **Why:** Explainability: a judge must see why a score moved.
- **How:** Each factor is `tanh(x / scale)`; score = 50 + 50 × Σ wᵢ fᵢ clamped to 0–100.
- **When:** Recomputed from the latest stored signals on each prediction read.
- **Where:** `scoring.py`, served at `/v1/predictions`.

The score publishes, per zone and future delivery hour, a 0–100 score, a
level (LOW below 40, MEDIUM 40 to below 70, HIGH at 70 or above), a
confidence, an expected value in $/credit, and a signed contribution with a
one-line explanation per factor (AC-GM-SCORE-01). The contribution of factor
i is 50 × wᵢ × fᵢ points. Because `tanh` is increasing and every weight is
positive, more outage capacity or a higher cited shadow price never lowers
the score (AC-GM-SCORE-02), nor does a higher temperature at or above 85 °F
or more active alerts (AC-GM-SCORE-05). The peak-period factor is +1 for an
on-peak hour and −1 otherwise, computed with the standard library calendar
and the six NERC holidays (AC-GM-SCORE-04).

Confidence = freshness × agreement, where agreement is the share of factors
whose sign matches the total and freshness is 1.0 when every input is younger
than twice its poll interval, else 0.6. Expected value = max(DA SPP, 0) ÷ 1000
× (1 + 0.5 × (score − 50) ÷ 50). Every prediction carries the disclaimer
"Simulation estimate, not guaranteed profit." (AC-GM-SCORE-03). Weights and
scales are named constants in `scoring.py`, the calibration knobs.

**Table 10 (T5): Score factors**

| Factor | Raw input | Scale | Weight |
|---|---|---|---|
| Price spread | DA SPP(z,h) − mean RT SPP(z) over the last hour, $/MWh | 50 | 0.18 |
| Load pressure | load forecast(z,h) − mean forecast(z) over the next 24 h, MW | 0.1 × mean | 0.18 |
| Outage pressure | outage capacity(z,h) − median over the next 168 h, MW | 0.1 × median + 100 | 0.18 |
| Congestion pressure | RT SPP(z) − RT SPP(HB_HUBAVG) + 0.1 × Σ cited shadow prices, $/MWh | 25 | 0.18 |
| Heat stress | max(NWS temperature − 85, 0), °F | 10 | 0.12 |
| Peak period | +1 on-peak, −1 otherwise | 1, not squashed | 0.08 |
| Weather alerts | count of active Severe or Extreme alerts | 1 | 0.08 |

#### 4.1.5 Decision router

**BLUF:** The decision router answers calibrated probability checks with baseline rules, scores itself with Brier scores, and acts on market state in exactly one case: marking a silent provider offline.

**Frame**

- **Who:** Judges reading the Predictions and router page; the owner during the outage demo.
- **What:** Check families, bands, calibration, and the optional Jev column (DES-GM-ROUTER, CONTRACT-GM-ROUTER).
- **Why:** Explainability and safety: probabilities are shown with their track record and never trade.
- **How:** A registry of check families evaluated every 60 s; results stored in `router_results`.
- **When:** Every 60 s; outcomes resolve when each horizon ends.
- **Where:** `decision_router.py`, `health.py`, `jev.py`, served at `GET /v1/router`.

The market family answers the DART spread check per zone and future delivery
hour: p = logistic(k × (score − 50) / 50 + b × sign(DA − last RT)) with
k = 2.0 and b = 0.3, horizon the end of the delivery hour, and outcome 1 when
the hourly RT average exceeds DA. `GET /v1/router` reports each check's band
and its Brier score over resolved results (AC-GM-ROUTER-01). The health family
(phase 2) estimates, for the ERCOT Worker and each provider, the probability
of becoming unavailable within 15 minutes from error rate, 429 rate, p95
latency, snapshot age, and heartbeat age (AC-GM-ROUTER-03).

Below 0.50 a result is logged for calibration, from 0.50 to below 0.80 it is
shown for review, and at 0.80 or above it raises an alert event. The router
holds no account key and submits no order (AC-GM-ROUTER-02). Its only acting
baseline rule marks a provider offline when its last heartbeat is older than
30 s; new sells from that provider's customers are then rejected with
`PROVIDER_OFFLINE` until the next heartbeat (AC-GM-PROV-04). With
`GRIDMARKET_JEV=on` the router adds the hosted Jev probability as a separate
column that changes no state; otherwise it makes no Jev call
(AC-GM-ROUTER-04).

#### 4.1.6 Bot population

**BLUF:** Sixty seeded bots of seven types trade through the public API with their own keys, and the whole population is reproducible from one master seed with the standard library alone.

**Frame**

- **Who:** The bots container and the owner who sets the master seed.
- **What:** Bot types, latent traits, households, and the per-bot trading loop (DES-GM-BOTS).
- **Why:** Agent population lens: diverse, reproducible traffic that exercises the real API and risk engine.
- **How:** `population.sample` with `random.Random(f"{master}:{index}")`, a Gaussian copula, and a pure-Python Cholesky factor.
- **When:** At first start on an empty database; each bot then loops on its own schedule.
- **Where:** `population.py`, `bots.py`, and the `bots` container.

When the database is empty the system seeds 60 bots of seven types; with
LoneStar Storage enabled at least 20 of them are its customers
(AC-GM-BOT-02). Seven latent traits (risk appetite, patience, reaction delay,
loss aversion, herd versus contrarian, daily activity, wealth) come from a
Gaussian copula with a fixed target correlation matrix, `statistics.NormalDist`
for the probit, and logistic-normal marginals for bounded traits. Each bot
gets 1 or 2 batteries, lognormal with median 13.5 kWh clamped to 5–40 kWh,
charge and discharge limits of 0.37 × capacity kW clamped to 2–10 kW, a
load zone from fixed weights, a 15–50% reserve habit, and a 24-weight
activity schedule (AC-GM-BOT-04). Two populations from one master seed have
the same SHA-256 digest, and 2,000 samples match the target medians, zone
shares, and rank correlations (AC-GM-BOT-08).

`bots.py` runs one loop per bot through the SDK with a key derived as `gm_`
plus the first 32 URL-safe base64 characters of HMAC-SHA256 of the bot
secret and `bot:<index>`, so the container needs only the secret. Each bot
submits at most 6 orders per rolling 60 s under the same risk controls as any
client (AC-GM-BOT-03), and the seeded traffic submits at least 10 orders per
minute from at least 3 accounts (AC-GM-BOT-01).

#### 4.1.7 Bot diversity and economy draws

**BLUF:** Blends, information limits, bounded learning, and a drawn economy make the population behave like many distinct households rather than seven clones.

**Frame**

- **Who:** Bots, the owner who spawns cohorts, and judges reading the Bots page.
- **What:** Diversity layers 2, 3, 5a, and 6, cohort spawn, and the economy draws (DES-GM-BOTS, DES-GM-ECON).
- **Why:** Diverse behavior makes market activity credible and dormancy meaningful.
- **How:** Dirichlet blends via `gammavariate`, per-bot signal subsets with delay, bias, and noise, and clamped threshold learning.
- **When:** At sampling, after each settled position, and on an admin spawn request.
- **Where:** `population.py`, `economy.py`, `bots_api.py`, and the Bots page.

Each bot blends its main type with 2 others using Dirichlet(6, 1.5, 1.5)
weights, sees only its subset of eight signal families, delayed 0–15
minutes, biased ±10%, and noised 2–10% (AC-GM-BOT-05). After each settled
position each decision threshold moves by at most its learning rate times its
range and is clamped; a restart replays settled positions from the ledger
(AC-GM-BOT-06). Evolution (layer 5b) is dropped and bots are never retired.

Starting cash is lognormal with median $1,000 and sigma 0.8, clamped to
$100–$10,000 and correlated with employment and risk appetite through the
same copula; 65% of bots are employed with lognormal pay of median $40
(AC-GM-ECON-01). An admin request to `POST /v1/admin/bots` adds a cohort of
1–10 bots with an optional seed, capped at 200 bots (AC-GM-BOT-07). The Bots
page shows the dormant rate and, when layers 2, 3, 5a, and 6 are landed,
trait coverage, behavior entropy, and a risk-against-patience scatter;
otherwise it marks them not enabled (AC-GM-UI-07). If S31 is not green by
Sat 14:00 CDT these layers move to phase 2.

#### 4.1.9 Dashboard and ERCOT Worker views

### 4.5 Fault Behavior

**BLUF:** GridMarket fails soft: data faults degrade to stale values, provider faults to typed rejections, and order faults to rejections that change no state.

**Frame**

- **Who:** Every feature under fault.
- **What:** Behavior when data sources, providers, or clients misbehave.
- **Why:** The demo must survive the faults it is likely to meet during recording.
- **How:** Backoff and stale marking, heartbeat-based offline marking, one-transaction rejections, and container restart.
- **When:** On any fault, until the source recovers.
- **Where:** Pollers, the router, the order path, and Compose.

ERCOT Worker or NWS failure triggers backoff from 5 s to 300 s while every
endpoint keeps answering from stored values marked stale with their age. A
provider whose heartbeat is older than 30 s is marked offline and its
customers' new sells are rejected until the next heartbeat. An asset offline
at delivery records a default and refunds the buyer. Every rejected order
changes no balance because the whole order path is one transaction. Rate
limits and the kill switch reject without side effects. If the process
crashes, Compose restarts it (`unless-stopped`) and state resumes from the
SQLite volume; bots rebuild from the ledger and master seed. The ML, backtest,
and qlib lanes never touch the live data path. The figure traces a Worker
outage from failure to recovery.

### 5.1 Considerations

**BLUF:** The threats that matter are abuse of the public API, replayed or duplicated orders, and credential leakage, and each has a control enforced before any state changes.

**Frame**

- **Who:** Anyone who can reach the tunnel; the owner at publication.
- **What:** Threats to the market, its data edge, and its secrets, with their controls.
- **Why:** A public demo invites automated abuse and secret scraping.
- **How:** Bearer keys stored as SHA-256, Idempotency-Key, token-bucket limits, and a secret scan over full history.
- **When:** On every request, and before the repository is made public.
- **Where:** `api.py`, `.env`, and the repository history.

A request to an account or trading endpoint without a valid key gets 401 and
changes nothing; keys are stored only as SHA-256 hashes (AC-GM-API-01). An
order that reuses an Idempotency-Key replays the original result for an
identical body, returns 409 for a different body, and returns 400 without a
key (AC-GM-API-02). A client over its rate limit gets 429 and changes nothing
(AC-GM-API-03). Before publication the repository has zero secret-scan
findings over its full history and an MIT `LICENSE` (AC-GM-SEC-01).

**Table 18 (T6): Threats and controls**

| Threat | Asset | Control | Residual risk |
|---|---|---|---|
| Unauthenticated trading | Accounts and ledger | Bearer key, SHA-256 storage | Stolen key until revoked |
| Duplicate or replayed orders | Balances | Idempotency-Key per account | None within stored window |
| Request flooding | Availability, feed | Per-key and per-address token buckets | Buckets reset on restart |
| Sandbox key farming | Market and feed | 3 keys per address per hour, 300 total | Distributed addresses up to the cap |
| Admin takeover from the internet | Bots, outage, kill switch | Admin key plus loopback without `CF-Connecting-IP` | Host compromise |
| ERCOT budget exhaustion | Shared ERCOT limit | Worker allowlist, key, per-client and upstream budgets | Per-location counting of rate-limit bindings |
| Credential leak | ERCOT, Cloudflare, Jev, bot, admin secrets | Untracked `.env`, no logging of keys, secret scan | Owner rotates on leak |
| Prompt injection via other users' text | User agents | MCP returns numbers, ids, and enums only | Text in user-supplied prompts |

### 5.2 Features

**BLUF:** Three security features guard state changes beyond ordinary trading: capped sandbox self-service, loopback-only admin requests, and an audited kill switch.

**Frame**

- **Who:** Visitors requesting sandbox keys and the owner acting as admin.
- **What:** Sandbox self-service, admin request gating, and the kill switch.
- **Why:** These are the paths where one request can create accounts or stop trading.
- **How:** Address and total caps, header and interface checks, and halts appended to the ledger.
- **When:** On each sandbox or admin request.
- **Where:** `api.py`, `keys.py`, and `adversary_api.py`.

`POST /v1/sandbox/keys` identifies the client by `CF-Connecting-IP` or the
socket peer, creates a $1,000.00 sandbox account at 5 requests/s and returns
its key once, and refuses with 429 after 3 keys per address per 60 minutes,
503 `SANDBOX_CAP` at 300 accounts, and 422 for a label outside
`^[A-Za-z0-9 _-]{1,24}$` (AC-GM-API-06). Any `/v1/admin/*` request carrying
`CF-Connecting-IP` or not arriving on loopback gets 403; on loopback a
missing or wrong admin key gets 401; neither changes state (AC-GM-API-07).
The dashboard's owner controls send a key typed by the owner and never store
it. The kill switch halts the market or one account until the same admin key
lifts it, and both halt and lift are appended to the ledger (AC-GM-ADV-02).

### 5.3 Interfaces

**BLUF:** Trust changes at three interfaces, the tunnel, the loopback, and the Worker key, and each carries exactly one credential or marker that the receiving side checks.

**Frame**

- **Who:** The market, the Worker, and the owner.
- **What:** Where trust changes and which credential or marker is checked there.
- **Why:** Naming each boundary's check makes a missing check visible in review.
- **How:** `CF-Connecting-IP` presence, the admin key, and `x-gridmarket-key`.
- **When:** On every crossing request.
- **Where:** Cloudflare tunnel ingress, host loopback, and the Worker's `/api/*` routes.

Requests through the tunnel always carry `CF-Connecting-IP`, which is the
client address for rate limits and sandbox caps and which disqualifies a
request from admin use. Requests on the host loopback without that header may
act as admin when they carry `GRIDMARKET_ADMIN_KEY`. The market authenticates
to the Worker with `x-gridmarket-key` equal to the Worker secret `MARKET_KEY`.
Bot keys are derived from `GRIDMARKET_BOT_SECRET`, so the bots container
holds one secret and no key list. Every secret lives in the untracked `.env`
or in Worker secrets and is never logged or returned.

## 6 Programming Model

**BLUF:** Programming GridMarket means calling its REST API, through the stdlib SDK, a rules template, the prompt kit, or gridmarket-mcp, and handling its typed errors and limits.

**Frame**

- **Who:** Developers and users' agents.
- **What:** The client programming model and the onboarding skill that teaches it.
- **Why:** A new person or agent must reach a live order quickly and safely.
- **How:** `from gridmarket import Client`; a fresh Idempotency-Key per order; typed error codes; documented limits.
- **When:** Any time the market is reachable.
- **Where:** `sdk/python/`, `examples/`, `docs/`, and `skills/gridmarket-onboarding/`.

A client creates a `Client` with its API key and the base URL, reads the
market and predictions, and submits orders; every order carries a fresh
Idempotency-Key. A client honors `Retry-After` on 429, reads the typed reason
on 422, and backs off on 423 while the market is halted. Order size is at
most 50 credits and the absolute position per product at most 200. The exact
SDK method names are frozen in `CONTRACTS.md` and documented in
`docs/USER_GUIDE.md`. The onboarding skill
`skills/gridmarket-onboarding/SKILL.md` takes a user's agent through getting a
key, reading data, choosing the SDK, template, prompt kit, or MCP, monitoring
its own orders, and handling each limit and error code (AC-GM-DOC-03).

## 7 Verification Approach

**BLUF:** GridMarket is verified by tests written before code in every lane, by deterministic gates at every assembly step, and by one uninterrupted acceptance run per phase.

**Frame**

- **Who:** Test Implementers, Product Implementers, the Integration Engineer, and phase assurance.
- **What:** How each requirement's verification method is applied.
- **Why:** A merged change that is not verified would put the demoable `main` at risk.
- **How:** Red tests, green implementation, write-set checks, post-merge V&V, and phase acceptance runs.
- **When:** Every slice, every assembly merge, and every phase landing.
- **Where:** `make` targets in the repository and the Lifecycle SEIT.

The Lifecycle's SEIT names, for each requirement, the method (test,
inspection, demonstration, analysis), the command, and the pass rule. Section
7.1 states the approach.

### Verification approach

**BLUF:** Every slice proves its write set, every assembly step proves the integrated branch still passes, and every phase lands only after one review, at most one repair, and green gates.

**Frame**

- **Who:** Every slice, the Integration Engineer, and the Orchestrator.
- **What:** The verification ladder from slice to landing.
- **Why:** Parallel lanes are safe only if each merge is checked before the next.
- **How:** Test-first lanes; `CMD-WRITESET`; backend tests, dashboard tests and build, and compose smoke after each merge; one phase review and assurance.
- **When:** At each slice exit, assembly merge, and phase landing.
- **Where:** Lane worktrees, `gridmarket/integration-<phase>`, and `main`.

Test Implementer and Product Implementer slices of a lane run in order in one
worktree, and a lane never merges red. Each slice changes only its write set,
and concurrent slices have disjoint write sets (AC-GM-LANE-01). After each
lane merge, the integrated branch passes the backend tests, the dashboard
tests and build, and the compose smoke run before the next merge; a red step
is reverted (AC-GM-LANE-02). A phase that passes assurance merges to `main`
through a PR whose merge commit passes the same gates, and its merged lane
branches and worktrees are then removed (AC-GM-LAND-01).

**Table 19 (T3): Verification gates**

| Gate | Command | When | Pass rule |
|---|---|---|---|
| Write set | `CMD-WRITESET` | Slice exit | No path outside the slice write set |
| Backend tests | `make test-all` | Slice exit, each assembly merge | Exit 0 |
| Dashboard | `make test-dash` | Each assembly merge | vitest and production build green |
| Smoke | `make smoke` | Each assembly merge | `/v1/market/status` answers from the compose stack |
| Secrets | `make secrets` | Before publication | Zero findings, MIT license |
| Specification | `make spec-lint` | Each spec change | Stable build, zero lint findings |
