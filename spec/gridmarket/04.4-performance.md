### 4.4 Performance

**BLUF:** GridMarket's performance budgets are request budgets toward its data sources and client rate limits, and any speed claim must come from the benchmark.

**Frame**

- **Who:** The pollers, clients, and the Rust lane.
- **What:** Request budgets, poll intervals, latency limits, and throughput evidence.
- **Why:** Staying under ERCOT's shared limit protects the whole demo; unmeasured speed claims mislead judges.
- **How:** Sliding-window limiters, token buckets, and one seeded benchmark workload.
- **When:** Continuously while the app runs; the benchmark runs once per engine.
- **Where:** `ercot.py`, `nws.py`, `api.py`, the Worker, and `bench/`.

The single SQLite writer caps order throughput at one write transaction at a
time; that is acceptable for the demo and would move to per-product locks or
Postgres only if load demanded it. The figure shows the polling cadence over
one hour. The Rust core is enabled only when the benchmark shows it faster.
