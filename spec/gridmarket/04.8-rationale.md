### Rationale

**BLUF:** Each major choice favors the smallest system that shows every success criterion live, and each choice records the ceiling it accepts.

**Frame**

- **Who:** Reviewers and judges asking why.
- **What:** The main architectural trade-offs.
- **Why:** Recorded trade-offs let a reviewer tell a deliberate limit from a defect.
- **How:** Compare the chosen option with its alternative on benefit and cost.
- **When:** Decided in planning (DEC-GM-*); revisited only by owner decision.
- **Where:** `design.md` decisions and the `ponytail:` comments in code.

The table records the trade-offs that shape the architecture.

Table (T4): Trade study

| Option | Benefit | Cost | Decision |
|---|---|---|---|
| One process and SQLite versus services and Postgres | One budget owner, trivial restart, no race on capacity | One writer at a time | One process and SQLite |
| ERCOT through the owner's Worker versus direct ERCOT client | Credentials and ERCOT budget in one owner-held place; views reuse it | Dependency on the Worker deployment | Through the Worker (DEC-GM-021) |
| REST polling versus WebSockets | One surface, simple tests | Up to 2 s display lag | Polling every 2 s |
| Deterministic tanh score versus ML model | Explainable and monotonic by construction | Possibly lower predictive power | Deterministic; ML only compared offline |
| Bots through the public API versus in-process calls | Exercises the real risk engine and limits | HTTP overhead | Public API (SC-9) |
| Contract-first parallel lanes versus sequential build | Many lanes at once within the hackathon | Wave 1 must freeze names up front | Contract-first (DEC-GM-039) |
| Cash-settled futures without margin versus a margin model | Simple, transparent P&L | A short can go below zero cash | No margin; shown on the dashboard |
