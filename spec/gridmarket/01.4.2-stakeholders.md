#### Stakeholders and their concerns

**BLUF:** Each stakeholder's main concern maps to one architectural answer, and the disclosures judges need are made in the product, not only in the pitch.

**Frame**

- **Who:** The owner, judges, traders and their agents, Jordan Hill, and lane implementers.
- **What:** Who cares about GridMarket and what each needs from it.
- **Why:** An architecture that ignores a stakeholder concern fails that stakeholder in the demo.
- **How:** Map each concern to the design element that answers it.
- **When:** Throughout the hackathon and at judging.
- **Where:** The dashboard, the README, the ERCOT Worker views, and the submission video.

The README carries a Contributors section stating that work Jordan Hill
contributes may be produced with a different agent or tool profile than the
owner's frozen Bearing profile and is integrated through the same lanes,
tests, and review gates (AC-GM-DOC-04). The Worker views and the dashboard
label router decisions from baseline rules as "baseline rules"; the hosted
Jev service is called only when its flag permits, and the README discloses
Jev as a pre-existing hosted service linked to the owner (AC-GM-RULE-02).

Table (T4): Stakeholders and their concerns

| Stakeholder | Concern | Architectural answer |
|---|---|---|
| Owner | A demo that never crashes and never leaks a credential | One process, stale-tolerant data, untracked `.env`, secret scan before publication |
| Judges | Can see why a score moved and trade within minutes | Factor contributions per score; sandbox key in two clicks; 30-line SDK example |
| Traders and their agents | One documented, rate-limited, idempotent API | CONTRACT-GM-API with OpenAPI, typed errors, Idempotency-Key |
| Jordan Hill | Worker and views keep working and keep attribution | Worker changes limited to S24–S27; authorship kept on `main` |
| Lane implementers | Parallel work that merges cleanly | Frozen names in `CONTRACTS.md`; disjoint write sets |
